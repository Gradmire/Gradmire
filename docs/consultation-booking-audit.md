### Lead endpoints (verified)

| Endpoint | Actual behaviour |
|---|---|
| `GET /api/v1/health` | Returns `{status:"ok"}`. Does not touch the database. |
| `POST /api/v1/leads` | 16 KB JSON body limit; whitelists known fields; `source` ∈ consultation/contact/newsletter (unknown → consultation); per-source required fields; inserts into `leads`. No rate limiting, no idempotency, no dedup. |
| `GET /api/v1/leads` | Requires `Authorization: Bearer $ADMIN_API_TOKEN` (constant-time compare). Returns latest 100 leads. No pagination. |

**Persistence:** leads are stored in PostgreSQL **when `DATABASE_URL` is set**
(production, CI). Without it `lead-store.js` falls back to an in-memory array
that is lost on restart. The README still says "intentionally in memory" —
that sentence is out of date.

## 2. Current booking and lead workflow

1. Visitor fills `free-consultation.html` (multi-step form: name, phone, email,
   intake, level, destination, interest, branch, consents).
2. `assets/api.js#submitLead` POSTs to `/api/v1/leads` with `source:"consultation"`.
3. A row is written to `leads`. Nothing else happens — no appointment, no slot,
   no counsellor, no confirmation email, no calendar event.
4. Staff can only read leads with the shared admin token via `curl`.

There is **no booking, scheduling, or appointment functionality** anywhere.

## 4. Existing database entities

Only two tables exist: `schema_migrations` and `leads`
(`id, source, first_name, last_name, email, phone, primary_destination,
intended_intake, study_level, service_interest, branch, country,
passport_status, referral_source, enquiry_type, message, contact_consent,
age_confirmation, marketing_opt_in, partner_institution_opt_in,

`branch_counsellors` and more, but **none of these exist** in migrations.

## 7. Security risks found

1. **Fake login** gives users a false sense that an account exists; anything
   shown on `dashboard.html` is not tied to an identity.
2. **Shared admin token** has no per-person identity, no rotation story and no
   audit; anyone holding it can read every lead.
3. **No rate limiting** on `POST /leads` — open to spam and enumeration.
4. **Cross-site API**: the site and API are on different `*.vercel.app`
   hosts, which are different *sites* (`vercel.app` is on the Public Suffix
   List). Any cookie-based session will be third-party there and blocked by
   Safari/Firefox and by Chrome when third-party cookies are disabled. A
   custom domain pair (`gradmire.in` + `api.gradmire.in`) or a working
   same-origin rewrite is required for production logins (see setup doc).
5. `GET /leads` returns PII with no pagination or field scoping.
6. Error handler logs full `pg` errors (may include values) — acceptable today
   but must not log request bodies.

## 8. Proposed (and implemented) design

- **Keep the architecture**: plain Node handlers, `pg`, SQL migrations. Add a
  tiny internal router and split code into `routes/` (HTTP), `services/`
  (business logic), `repositories` inside services via SQL, and
  `integrations/` (calendar, email) with provider adapters.
- **Auth**: `users` + `sessions` tables, scrypt password hashes, random
  session token in an `HttpOnly` cookie (only its SHA-256 hash is stored),
  per-session CSRF token sent in `X-CSRF-Token`, Origin allow-list check on
  state-changing requests, roles `student` / `counsellor` / `admin`. Email
  verification tokens. Staff accounts are created only via a CLI script.
- **Booking**: consultation types and counsellor availability are data.
  Slots are computed server-side from weekly rules (in the counsellor's
  timezone), date exceptions, buffers, notice/advance windows, existing
  bookings and (when configured) Google Calendar free/busy. Creation re-checks
  everything inside a transaction; a PostgreSQL **exclusion constraint**
  (`btree_gist`) makes overlapping active bookings for a counsellor (or for the
  same student email) impossible even under concurrency. `Idempotency-Key`
  makes retries safe.
- **State machine**: `reserved` (slot held, calendar not yet synced) →
  `confirmed` → `completed` / `no_show`; `cancelled`; `rescheduled` (old row,
  linked from the new one).
- **Guests**: lead created or safely reused (same normalised email **and**
  phone); a one-time manage token (hash stored) lets guests view/cancel/
  reschedule and later claim the booking. Bookings are linked to an account
  only by that token or after the account's email is verified.
- **Outbox jobs**: calendar sync jobs and notifications are rows in
  PostgreSQL, claimed with `FOR UPDATE SKIP LOCKED`, retried with back-off,
  de-duplicated by unique keys, and run by a cron-triggered endpoint or a
  long-running worker.
- **Calendar**: adapter interface with a Google Calendar provider (service
  account, deterministic event IDs so retries cannot duplicate events,
  optional Meet links) and a `none` provider.
- **Email**: adapter interface with a Resend provider and a `disabled`
  provider that records notifications as `skipped` — never as sent.
  WhatsApp is a documented stub (owner chose email-only for now).

## 9. Dependencies and deployment requirements

- PostgreSQL 13+ with the `btree_gist` extension (available on Neon and in
  the CI `postgres:16` image). Migration `004` runs
  `CREATE EXTENSION IF NOT EXISTS btree_gist`.
- New dev-only dependency: `embedded-postgres` (real PostgreSQL binaries for
  local tests without Docker). No new runtime dependencies.
- New environment variables (session secret, cookie settings, cron secret,
  calendar and email credentials) — listed in `backend/.env.example` and the
  setup guide. Nothing works with invented credentials; integrations stay
  disabled until configured.
- A scheduler that calls the job endpoint every 5 minutes (Vercel Cron on Pro,
  or an external scheduler on Hobby — Vercel Hobby cron runs at most daily).
- Same-site hosting for site and API for cookie sessions (see §7.4).
