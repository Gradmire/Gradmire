# Role-Based Dashboards — Repository Audit

Audit date: 20 October 2026 · Branch: `feat/mbbs-country-pages` (head `fd3b4ab`)

This audit records what the repository contained **before** the role-based
dashboard work, verified by reading the code and running the test suite
(`npm run check` clean; `npm test`: 49 passed, 0 failed, against a real
embedded PostgreSQL 16). The earlier booking audit
([`consultation-booking-audit.md`](consultation-booking-audit.md)) describes
the state before accounts existed; this one starts where that work ended.

---

## 1. What currently exists

| Layer | What exists |
|---|---|
| Frontend | Static HTML in `frontend/pages/` (64 pages). Signed-in pages are generated by `scripts/build-booking-pages.mjs` and `scripts/build-dashboard-pages.mjs` from `scripts/page-shell.mjs`; data is loaded at runtime by page scripts in `frontend/assets/` through `api.js` (`GradmireAPI.request`, CSRF handling, session cache). No framework, no build step. |
| Backend | Plain Node.js ≥ 20 (`node:http`, ESM) in `backend/`. One handler (`src/app.js`) for the local server and the Vercel function. `src/routes/booking-api.js` uses a small router (`src/lib/http.js#createRouter`), a per-request context with origin + CSRF checks (`src/routes/context.js`) and a whitelisting validator (`src/lib/validate.js`). Business rules live in `src/services/`. Single runtime dependency: `pg`. |
| Database | PostgreSQL (Neon in production). Migrations `schema/001–005` applied once each by `scripts/migrate.js` under an advisory lock; `*.down.sql` are manual rollbacks. |
| Auth | First-party: scrypt password hashes, opaque session token in an HttpOnly cookie (only SHA-256 stored), per-session CSRF token, login lockout after 10 failures, email verification with HMAC-derived single-use tokens. Sign-up always creates a `student`. |
| Roles | `users.role` ∈ `student`, `counsellor`, `admin` (CHECK constraint). Staff are created only by the CLI `npm run create-staff`. Guards: `requireStudent`, `requireStaff`, `requireAdmin`. Role and status are re-read from the database on every request (`loadSession` joins `users`), so a role change takes effect on the next request. |
| Booking | Consultation types, weekly availability + exceptions, server-side slot derivation, exclusion constraints against double-booking (per counsellor and per student email), idempotency keys, reschedule chain, guest manage links (HMAC token, only hash stored), calendar outbox, email outbox with retries and honest `skipped` status when no provider is configured. |
| Guest → student | On email verification, guest consultations and leads with the **same verified email** are linked to the account (`auth-service.js#linkGuestRecords`). A guest booking can also be claimed with its manage token, but only by a verified account whose email matches the booking (`booking-service.js#claimConsultation`). |
| Student area | `dashboard.html` (journey, applications, next consultation), `dashboard-consultations.html` (list, cancel, reschedule, claim). |
| Staff area | `admin-consultations.html` (CRM: list/filter, detail drawer, notes, follow-ups, outcome, reassignment for admins, availability editor scoped to own calendar for counsellors). `admin-students.html` (record university applications). Counsellors only reach consultations assigned to them and students who booked with them. |
| Audit | `audit_log` (append-only) for auth events and staff actions; `consultation_events` for booking history. |
| Leads | `leads` table fed by the contact, consultation-request and newsletter forms (`POST /api/v1/leads`) and by bookings. `GET /api/v1/leads` needs a shared bearer token. |
| Integrations | Email via Resend (optional), Google Calendar (optional), WhatsApp interface stub (not implemented). |
| Tests | `node --test` suites: booking, security, integration, applications, time — 49 tests on a real PostgreSQL. CI runs them plus link checks. |

## 2. What works (verified)

- Sign-up, login, logout, lockout, session expiry, CSRF and origin checks.
- Guest and student booking with real availability; double-booking prevented by the database.
- Guest manage link (view, cancel, reschedule) and claim into an account.
- Email-verification-driven linking of guest bookings and leads.
- Assignment-scoped counsellor access to consultations and students; admin-only reassignment and consultation-type management.
- Student application records written by staff, read by the student.

## 3. What is incomplete

- **Leads have no lifecycle.** No status, owner, contact attempts, follow-up date, or staff UI. Staff can only read the latest 100 leads with a shared token.
- **Student profile** is limited to name/phone on `users`; booking preferences are stored per consultation and lead, not on the student.
- **Notifications** are email-only; there is no in-app notification centre.
- **Follow-ups** exist only as notes attached to a consultation; they cannot be linked to a lead or a student without a booking.
- **Guest booking retrieval** relies entirely on the original email; a guest who lost it has no self-service way to get the link again.
- **Admin dashboard** has consultation counts but no platform metrics (students, leads, staff).
- Login sends every non-student to the consultations CRM; there is no role-specific landing page.

## 5. Tables that can be reused

| Table | Reuse |
|---|---|
| `users` | Kept as the single identity. A person keeps the same `id` when they become staff. `role` gains `super_admin`. `status` (`active`/`disabled`) becomes the suspension switch. |
| `sessions` | Revoked on suspension, role change and access revocation. |
| `counsellors` | Is the consultant's working profile (availability, buffer, calendar). Deactivated, never deleted, on revocation so historical consultations keep their foreign key. |
| `consultations`, `consultation_notes`, `consultation_events` | Unchanged; reassignment logic is shared with revocation. |
| `leads` | Gains status, assigned counsellor and next follow-up. |
| `student_applications` | Unchanged (university applications). |
| `notifications` | Email outbox gains non-consultation templates (invitations, application decisions, access changes). |
| `audit_log` | Used for every privileged action; a viewer is added. |

## 6. APIs to modify or create

- **Modify:** guards to understand `super_admin`; login landing per role; `isAdmin` checks in admin and application services; reassignment logic extracted so revocation can reuse it; notification renderer for payload-only templates.
- **Create:** student profile/overview/notifications; consultant applications (applicant + reviewer); employee invitations and acceptance; approvals (list, approve, reject, request information); user management (search, detail, suspend, reactivate, role-change and revocation requests); lead management; follow-up tasks; consultant overview; admin overview; audit log; guest "resend my booking links".

## 7. Security risks and architectural limitations

1. **Privilege changes only by CLI or SQL.** `create-staff --promote` changes a role with no second approver and no per-person audit actor. Mitigation: approval requests with a two-person rule; CLI stays as the bootstrap path and is audited.
2. **Shared admin token** for `GET /api/v1/leads` has no identity. It is kept for backward compatibility; the new session-based lead endpoints are the supported path.
3. **Cross-site cookies.** The site and API are on different `*.vercel.app` hosts. Session cookies are third-party there and blocked by Safari/Firefox (documented in the booking setup guide). Production needs a shared custom domain. This affects every dashboard equally.
4. **No object storage.** CV and document uploads cannot be stored privately, so they are **not implemented**; the CV field accepts an optional `https://` link, shown only to reviewers.
5. **Single role per user.** A person who becomes staff stops using the student area (their records stay attached to the same id). Acceptable for Gradmire's size; documented in the architecture doc.
6. **Bootstrap.** The two-person rule means the first super admin must be created with the CLI, and activating the first admins needs two privileged people. Documented in the setup doc.
